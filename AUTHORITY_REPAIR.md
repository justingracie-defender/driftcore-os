# DriftCore authorization repair — September 13 base, updated 20 September 2026

The two reported authorization gaps have been repaired in the guard and broker
paths, without changing model weights or calling a model. This is a tested code
repair with an explicit deployment boundary. Operating-system isolation has not
been verified in this sandbox, and the complete project is not all green here.

In plain language: the agent can propose an action, but its assertion that an
action is authorized no longer grants permission. The trusted execution service
checks permission against a separately configured authority and checks the actual
action parameters before executing. Whether the model sounds convincing does not
change these checks.

## What changed

| Finding | Repair | Boundary of the claim |
|---|---|---|
| R2: the caller can assert `target_authorized=True` | Legacy permission flags and human-name labels grant no permission. The guard defaults to refusing conditional egress/account access. An operator-installed policy validates structural targets. | The guard verdict alone does not execute or sandbox anything. |
| R3: the caller can install its own global identity verifier | Signed guard policies and execution approval gates retain their explicitly supplied verifier, seal its principal registry, and ignore later global-verifier replacement. | Arbitrary Python inside the trusted broker process can still tamper with that process. OS separation and key custody are required. |
| Permission can be substituted between requests | Signed guard approval covers action, effects and exact target strings. The existing broker approval/grant binding covers the actual actuator, command, parameters, broker, subject and declared effects. | Cryptographic validity proves approval by the configured key, not that a human understood the request. |
| Account access could omit a destination declaration | Both `ACCOUNT_ACCESS` and `DATA_EGRESS` require a destination parameter when registering a protected actuator and consult the execution destination interlock. | Actuator declarations and implementations must be installed by trusted bootstrap code. |
| Production configuration could omit human approval | `ProductionActuationBroker` requires `HumanApprovalGate`, in addition to its existing mandatory controls. | The base `ActuationBroker` remains available for development and compatibility. |

Additional changes:

- `human_identity.seal_policy()` lets trusted startup code lock the process-wide
  attested policy. Its public reset, downgrade, verifier replacement and principal
  registration APIs then refuse changes. There is no public unseal operation.
- Registration copies key material to immutable bytes. Sealing a verifier prevents
  later public additions and replacements, including through a retained handle.
- Unconditional constitutional prohibitions run before spending a conditional
  approval. Invalid effect types, authorizer failures and non-Boolean success
  values fail closed.
- Installing a coordinator standing policy preserves a custom guard's overridden
  safety checks and leaves the original guard unchanged.
- `eval_harness.py` uses a private, pinned demo verifier and exact approvals. It
  does not replace an importing application's global identity policy. Its test key
  is public demonstration material and must not be used for deployment.
- Existing success tests now obtain explicit approvals; R2/R3 regressions now
  require the attacks to fail. A legitimate action must still succeed.

The broker's early constitutional check intentionally delegates conditional
authorization to its later destination, grant and human-approval checks. An early
pass is not an execution permit. The old fictitious broker-as-human label is gone.

## Additional repair: SQLite startup contention

`SqliteNonceStore` used a busy timeout but assumed WAL negotiation would always
wait for it. During simultaneous cold starts, SQLite can return `SQLITE_BUSY`
immediately. The old constructor raised `NonceStoreCorrupt`, and affected workers
never reached their nonce writes. This explains the intermittent receipt and
nonce-conformance failures; it was not evidence of two agents successfully
spending the same approval.

Initialization now retries only SQLite lock/busy errors within a monotonic wait
budget. The remaining budget is also passed to SQLite, so successive attempts do
not each receive a fresh full wait period. Exhaustion raises `NonceStoreLocked`.
Other database errors still refuse, and unsuccessful construction closes its
connection. Schema initialization is repeatable; retries consume no approval.

`busy_timeout_ms` now accepts a non-negative integer in SQLite's 32-bit range;
booleans, fractions, non-finite values and out-of-range values refuse construction.
Numeric SQLite error codes are used when available. For Python 3.10 compatibility,
which the project README promises, the fallback accepts only the exact lock
messages; unknown errors are not retried. This run used **Python 3.12.14**. The
missing-error-code branch is covered by fixtures; an actual Python 3.10 runtime
was not exercised here.

## Integration instructions for Claude or Grok

1. Compare the starting archive hash before applying `authority-repair.patch`.
   On this exact base, apply from the project root with `patch -p1`. If another
   branch has moved, review and merge the diff; do not overwrite newer work.
2. Construct authorities only in trusted startup code. Register principal keys
   before constructing `HumanApprovalGate` or `SignedEgressApproval`, because those
   constructors seal the verifier. Rotate keys through a controlled service
   restart/configuration replacement. Do not accept a verifier, authorizer or
   policy constructor from an agent request.
3. Use `SignedEgressApproval` for an action-specific guard decision, or an explicitly
   installed `StandingEgressPolicy` for standing permission. `declared_by` is an
   audit label, not authentication. Standing targets use exact strings; there is
   no wildcard expansion. Approval effects must include any backstop-inferred
   effects, or the mismatch refuses.
4. Execute protected actions through the existing broker. Register trusted
   actuators with their complete effects and destination parameter. Use
   `ProductionActuationBroker` for production, supplying the required approval,
   halt, evidence and isolation configuration. Never turn a guard's Boolean
   verdict into a reusable execution credential.
5. Put the agent under a separate OS identity without the broker's keys, writable
   code/configuration, privileged file descriptors or direct actuator/network
   capabilities. Protect the broker and the approval service from agent-supplied
   Python and plugins. Run the existing isolation attestations and monitor for
   capability restoration; another process alone is not sufficient.
6. Use durable, atomic nonce stores for both approval and grant verification when
   approvals must remain single-use across restarts or multiple brokers. The
   focused authorization tests use temporary, in-memory stores and establish
   same-lifetime replay rejection. The separate SQLite tests check concurrent
   single-use and persistence after reopening the database; they do not establish
   durability through every possible crash or storage failure.
7. On a disposable Linux host with working Unix sockets and permission to switch
   child UIDs/GIDs, run `python3 scripts/verify_authority_isolation.py`. Exit 0 must
   show denied key reads and direct writes, rejected forged/modified requests,
   and exactly one authorized file effect. Exit 77 means unavailable. This test
   deliberately makes no external network call and does not certify network
   isolation or the full production profile.
8. Run the official full suite, the focused authorization tests and the
   authorization, SQLite-startup and audience mutation runners as separate
   commands, preserving each exit code. Do not report the
   package as production-verified until socket/isolation checks run successfully
   on the intended host and the remaining project gates are reviewed.

## What remains outside this repair

This does not establish universal honesty, inspect the model's intentions, or
prove that every authorized task is safe. No such claim is needed to fix R2/R3.
The concrete property is that an untrusted request cannot replace the checked
authority or grant itself permission through these paths, assuming the broker,
keys, configured policy and execution boundary remain protected.

R1's effect-classification limitation remains: arbitrary language can describe a
harmful action without matching a text backstop. Trusted actuator declarations
and capability confinement must supply the real effects. The existing broker
egress policy matches scheme/host/port; it is not a new path/query content filter.
Approved channels can still carry harmful or secret content if the approval
policy permits it. Model persuasion, misleading approval displays, key theft,
unmediated tools, covert channels and compromise of the trusted execution service
need their own controls and tests. None is silently declared solved here.
